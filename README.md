# Оптимизация синхронизации CRM в PostgreSQL

## Узкие места исходного кода и решения

1. **N+1 и отдельный commit на каждую запись**
- Было: на каждого покупателя и сделку выполнялся отдельный SELECT через `@>` и сразу `db.session.commit()`. Для 70 тыс. сущностей это создавало более 70 тыс. транзакций и 150+ тыс. запросов к базе.
- Сделано: перевел обработку на батчи по 2000 записей. При старте один раз забираем легкий индекс (`SyncIndex`) по id и логинам. Поиск и сопоставление выполняются в памяти за O(1), а изменения сохраняются пачками с одним коммитом на батч.

2. **Чтение всей таблицы и дорогая чистка**
- Было: в конце вызывался `select(AbstractCustomer).all()`, поднимая всю таблицу с тяжелыми JSONB-полями в память. Внутри крутились циклы с коммитом на каждый элемент, а в `NOT IN` передавался массив из десятков тысяч id.
- Сделано: удаление неактуальных записей выполняется чанками по первичному ключу. Фильтрация вложенных сущностей и слова "удалить" запускается только для изменившихся записей, без выгрузки всей таблицы в память.

3. **Баги в логике и падения**
- В `lead_action` при слиянии записей стоял ранний `return`, из-за чего сама сделка терялась. Теперь данные корректно объединяются, лид сохраняется, а дубль удаляется.
- В `amocrm.py` у лида не извлекались контакты из `_embedded` (всегда оставался пустой список). Добавил корректный парсинг.
- В `filter_merge_abstract_customer` была опечатка в переменной цикла (`l` вместо `c`) и риск падения при `name=None`.
- Обернул сбор в общий блок: если выгрузка оборвалась с ошибкой, удаление записей не запускается.

## Схема данных (что оставлено)
Таблица `abstract_customer` и формат JSONB сохранены без изменений. Это исключает поломку внешних сервисов, которые читают эти структуры. Чтобы поиск по логину и названию из других частей системы работал быстро, добавлены GIN-индексы с `jsonb_path_ops`.

## Оценка ресурсов (20 тыс. покупателей, 50 тыс. сделок)
- Запросы к Postgres: порядка 80-100 запросов на весь прогон вместо 150+ тысяч (предзагрузка карты id, пакетные операции по 2000 штук и точечная чистка).
- Память: пиково около 80-110 МБ. В памяти хранится плоский словарь id и логинов (~25-35 МБ) и текущая пачка объектов, которая сбрасывается через `expunge_all()`.
